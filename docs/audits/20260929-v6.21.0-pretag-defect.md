## P1-1  When the owning directory disappears, the other directory switches to the plain id: its own memories become invisible and it is shown the gone directory's memories. A session that is running at that moment is split in two.

Where: project-utils.mjs:85 (`readProjectOwner` treats a missing directory as no owner),
project-utils.mjs:106, lib/project-owner.mjs:130 (the sweep), hook.mjs:2777 (the re-key
sources are only `legacy` and `plain`, never `<plain>~<hash>`).

Mechanism: B does not own the id and has collected its rows under `packages--api~<hashB>`.
When A's directory stops existing (a deleted worktree/checkout, or even a volume that is
unmounted for a while), `projectIdForDir(B)` returns `packages--api` straight away. The next
SessionStart elects B, because A's paths fail `existsSync`. Nothing ever moves `~<hashB>`
back to `packages--api`. The re-key only moves INTO the hashed id.

Repro (`node .probe-owner/p2-owner-gone.mjs`):
```
B id after first start: packages--api~b344973e
before A deleted: packages--api = a1..a3 ; packages--api~b344973e = b1,BRAVOROW_NEW,b-no-path
B id right after A deleted (no new SessionStart): packages--api
B id after next start: packages--api
after:  (unchanged) packages--api = ALPHAROW_ONE,a2,a3 ; ~b344973e = b1,BRAVOROW_NEW,b-no-path
B context mentions BRAVOROW_NEW: false   mentions ALPHAROW_ONE: true
```
The SessionStart context for B now shows A's memory and none of B's own. The CHANGELOG
names `.claude/worktrees/<name>` as the case this fixes, and worktrees are exactly the
directories that get deleted. The rows are intact, but only `--project <id>~<hash>` reaches
them, and nothing tells the user that id.

Mid-session variant (`node .probe-owner/p6-midsession-flip.mjs`, live CLAUDE_PID):
```
before A deleted: ep-packages--api~0fa65d02@h<pid>.json, session-packages--api~0fa65d02@h<pid>
after A deleted + Stop: ep-packages--api~0fa65d02@h<pid>.json (STILL THERE), session-packages--api@h<pid>, session-...~0fa65d02@h<pid>
sdk_sessions: hook-packages--api~0fa65d02-…  AND  hook-packages--api-…   (one host session, two memory sessions)
```
Stop flushed only the buffer under the plain id. The first buffer (the BRAVO_ONE edit) has
an id that no SessionStart in B will ever look for again, so the 7-day sweep deletes it.

Also: sweepDeadProjectOwners runs on EVERY project's SessionStart. If A's directory is
missing only briefly (an external disk, a network home), A's record is deleted, and a B
SessionStart in that window takes the id for good.

## P1-2 (Windows; rests on one host fact I could not run)  On Windows the hooks and the MCP server get different project ids, for every project

Where: project-utils.mjs:42-48 (`canonicalProjectDir` removes only trailing separators and
applies NFC), project-utils.mjs:106 (plain string `===`), lib/project-owner.mjs:82 (the
record stores the hook's spelling).

Host evidence, from the Claude Code 2.1.284 binary on this machine
(`~/.local/share/claude/versions/2.1.284`):
- Hook env: `mt=O()==="windows", nt=shell==="powershell", vt=e.args!==void 0 … let Mt=mt&&!nt&&!vt?(Tr)=>Tr.replaceAll("\\","/"):(Tr)=>Tr … CLAUDE_PROJECT_DIR:Mt(bt)`.
  So on Windows, with a non-PowerShell hook shell and a string-form command (all of ours,
  hooks/hooks.json), hooks receive `C:/Users/u/proj`.
- MCP env: `env:{...,CLAUDE_PROJECT_DIR:Ue??wr(),…}` with no conversion. The MCP server
  receives `C:\Users\u\proj`.

Simulation with win32 path semantics (`cd .probe-win/wd && node --import ../register.mjs ../sim.mjs <rt>`):
```
plain id  hook: u--proj  mcp: u--proj
id        hook: u--proj  mcp: u--proj~574313da
```
SessionStart writes an owner record for EVERY project, not only for contested ids. So once
any session has started in a project, the MCP face (mem_save's default project, the
mem_search/mem_recent/mem_recall scope, currentProject ranking) uses a different project
from the hooks. Before this release both faces computed `u--proj`. The CLI from Git Bash
reads PWD (`/c/...` or `C:/...`) and is probably a third spelling.

Uncertain because: I did not run on Windows, and I did not confirm that the default hook
shell there (`_1()`) is bash rather than PowerShell. The README says 4 hooks need Git Bash.

## P2-1  One directory reached through two spellings gets two ids. The election can even give the id to the other spelling of the same directory.

Where: project-utils.mjs:106 and lib/project-owner.mjs:49-61 compare path strings. Neither
calls realpath.

Repro (`node .probe-owner/p1-symlink.mjs`; `link/work` is a symlink to `real/work`; rows
recorded under the real spelling):
```
owner: …/p1/real/work/api
id for logical spelling: work--api~361be4ff     id for real spelling: work--api
rows: work--api = 2 ; work--api~361be4ff = 1
notice: "this directory's memory now has its own id, work--api~361be4ff, because work--api belongs to …/real/work/api"   (itself)
```
Terminal CLI, same directory (`node cli.mjs recent 5`, CLAUDE_PROJECT_DIR unset):
```
standing in real/work/api:  [mem] Recent (work--api):  #2 beta, #1 alpha
standing in link/work/api:  [mem] Recent (work--api~361be4ff):  #3 gamma
```
Shapes this covers: macOS `/tmp` vs `/private/tmp`, `~/Dropbox` vs
`~/Library/CloudStorage/Dropbox`, a symlinked `~/code`, and case differences on macOS
(case-insensitive). Before this release all of these gave the same id, because only the
last two path components count. The terminal CLI and the Bash-tool CLI read PWD, and the
Bash tool gets no CLAUDE_PROJECT_DIR (verified). So `recent`/`search` come back empty and
`save` writes to an id nothing else reads. A session started from an IDE (real path) and one
started from a terminal (logical path) also split permanently.
Not checked: whether Claude Code's own CLAUDE_PROJECT_DIR is the logical or the physical
path. The binary keeps both `projectDir` and `projectDirReal`.

## P2-2  The re-key's `LIKE` ignores ASCII case, so it moves ANOTHER directory's rows (even the owner's) into this directory's project

Where: lib/project-rekey.mjs:46-47 (`f.filename LIKE '<root>/%'`). SQLite LIKE is
case-insensitive for ASCII, and the repo never sets `case_sensitive_like` (grep: none).
The election and `legacyIdIsExclusive` compare case-sensitively, so the three disagree.

Repro (`node .probe-owner/p7-like-case.mjs`; Linux, `…/repo/packages/api` owns the id,
`…/Repo/packages/api` is a different directory with the same id):
```
owner: <base>/repo/packages/api
[ { project: 'packages--api~0394d8a9', t: 'ALPHA_1,ALPHA_2,ALPHA_3,BRAVO_1' } ]
```
All three of the owner's memories moved to the non-owner's hashed id, and the owner has
none left. The D9 path runs the same function with the same flaw (for example
`/home/A/projects/博客` and `/home/a/projects/博客` share `projects----`). The `=` arm is
exact. Only the LIKE arm has this problem. A GLOB, or `substr(f.filename,1,n)=?`, would be
case-exact.

## P3

P3-1  stripPrivate is quadratic again, on `<private ` with no `>`. lib/private-strip.mjs:39
`/<(\/?)private(?:\s[^>]*)?>/gi`: each opener's `[^>]*` runs to the end of the input.
`node .probe-owner/p4-private-redos.mjs`:
`"<private " x n` takes 76 ms (45 KB), 308 ms (90 KB), 1230 ms (180 KB) and 4731 ms (360 KB),
and `"</private " x n` behaves the same. Each doubling costs 4×. `<private>`-dense input stays
around 1-4 ms. At the 256 KB hook stdin cap that is about 2.5 s per prompt or tool response
that carries such text (hook.mjs:3306, secret-scrub.mjs:885, utils.mjs:352). The linearity
test (tests/private-strip.test.mjs:124) only feeds `<private>`, so it cannot catch this.
`[^<>]*` would stop the scan at the next tag.

P3-2  An adopted orphan buffer loses its Read paths. hook.mjs:517 collects

after adoption `reads-@h<dead>.txt` is still there. In the no-pid mode (pre-D14 names) the
same run consumes `reads-work--todo-app.txt`.

## Answers by question

Q1 identity: yes to "moved into ANOTHER directory's project" (P2-2), yes to "lost" (P1-1:
stranded, not deleted), and yes to "faces compute different ids" (P1-2 Windows, P2-1 spelling).
I found no path that moves one row twice. The re-key is idempotent across re-runs, and the
marker is written only after the loop. First-claim races are safe (`linkSync` EEXIST);
dead-record races are not (P3-6). NFC/NFD and trailing slashes are handled in both
languages. On Linux an NFD-named directory can never hold a record, because the record
stores NFC and `existsSync` compares bytes. I did not probe that (rare).
Truncation to 100 bytes and the `~hash` suffix keep file names under 255 bytes.

Q2 session state: without CLAUDE_PID the file names match 6.20 byte for byte (tests pass
CLAUDE_PID=''). A recycled pid reads as alive, so its files are kept (the safe direction).
spawnBackground inherits CLAUDE_PID (hook-shared.mjs:588 `...process.env`). The MCP server
has no CLAUDE_PID but never touches host-scoped files (grep: only hook*.mjs). Loss paths:
P1-1 (flip), P3-2, P3-3, P3-7. Double-flush is possible only if a live host is misclassified
as dead: adoption takes the ADOPTER's lock (hook.mjs:3034-3040), not the orphan owner's. That
needs a data dir shared across pid namespaces or machines. Not probed.

Q3 maintenance: no wrong-delete path found. The queue pass (maintain-core decayAndMarkIdle)
carries every hide guard plus superseded_at, access and injection counts. Parameter order
matches the SQL (`hidden_at < ?`, then projectFilter; `SET hidden_at = ?`, then
`created_at_epoch < ?`). `NOT IN` cannot hit NULLs (`WHERE compressed_into > 0`). Hard delete
is still only purge_stale with confirm. Downgrade to 6.20 and back: 6.20 ignores hidden_at
and never un-hides -1, and its own -1 writes leave hidden_at NULL (never queued), so no
surprise deletes. One behaviour change to be aware of: rows markAutoCompressible hid in the
CURRENT project were never deletable in 6.20, and now become purge-eligible 7 days later.
The CHANGELOG covers this ("every project").

Q4 invariants: the new recallByFile ORDER BY ends in `id DESC`. The election's
`SELECT DISTINCT … LIMIT 5000` has no ORDER BY. It is a sample, and above 5000 paths it
decides on whichever rows SQLite returns first. No new `.pipe()` zod schemas (memRecall
`project` is a plain optional string; defer title uses `.refine`). The liveness predicate is
applied where rows are read (recallByFile). Writes that change project are the re-key, which
is cross-project by design.
