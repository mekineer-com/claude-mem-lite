## 1. P1 — 已证实 — B-6 removed the only bound on the shared marker; the seen-set now grows for the life of the session, and pre-tool-recall's own docblock names the consequence

`lib/injected-ids.mjs:136-139`

```js
  const ids =
    mode === 'union'
      ? [...new Set([...prev.ids.map(String), ...newIds.map(String)])]
      : [...newIds, ...carried];
```

Before this commit `mode:'replace'` wrote `newIds` as the whole array. That was the defect B-6 fixes — and
it was also the **only** thing that ever shrank this file. `union` has always accumulated; `replace` was the
reset. Both arms now only grow, and `ts: Date.now()` (`lib/injected-ids.mjs:144`) is rewritten on **every**
write, so `readInjectedMarker`'s staleness gate never fires in a session where any hook writes within
`DEDUP_STALE_MS` (5 min) of the previous write — i.e. any ordinary agentic session.

**Reproduced** (`scratchpad/probe/growth.mjs`, 40 rounds of 5 pre-tool-recall triggers + 1 UPS prompt each —
a deliberately modest tool:prompt ratio):

```
round  1: ids=  13  bytes=   156  count=6 upsCount=1
round 10: ids= 130  bytes=  1022  count=60 upsCount=10
round 20: ids= 260  bytes=  1983  count=120 upsCount=20
round 40: ids= 520  bytes=  3903  count=240 upsCount=40
```

Linear and unbounded. The prior ceiling was "ids accumulated since the last UPS prompt"; the measurement
recorded in this repo for that ceiling is `scripts/pre-tool-recall.js:92-93` — "id-count histogram 1x9, 2x1,
3x2, **16x1** over n=13".

Why that matters is already written down, five lines further on at `scripts/pre-tool-recall.js:100-105`:

```
// The residual failure mode that premise was hiding, derived from the arithmetic and NOT
// observed in the wild: at a seen-set of 16 the slack still caps at 5, so a Read fetches
// obsLimit = 6, and if all 6 are in the seen-set the face goes silent again — the exact
// failure ALGO-4 exists to fix.
```

The arithmetic is at `scripts/pre-tool-recall.js:598-600`:

```js
    const crossHookSeen = readCrossHookInjected(project, sessionId);
    const dedupSlack = Math.min(crossHookSeen.size, CROSS_HOOK_DEDUP_SLACK_MAX);   // cap 5
    const obsLimit = (isRead ? 1 : 2) + dedupSlack;
```

and the filter it feeds at `scripts/pre-tool-recall.js:720-723`. The seen-set sizes the over-fetch up to 5
and then drops every fetched row that is in it. At 16 the repo called this a derived-not-observed risk. At
520 it is the ordinary case: a Read fetches 6 candidates against a 520-entry seen-set.

Second-order, same root cause: `shouldSkipByDedup` (`scripts/prompt-search-utils.mjs:251-253`) computes
`overlapCount / newIds.length >= 0.8` against `prevIds`. `prevSet` is now strictly larger than it was —
monotonically, all session long — so the UPS face is suppressed more often too. Measured in the same probe:
five ids that pre-tool-recall showed 40 rounds earlier still return `shouldSkipByDedup(...) = true`. That is
the same face B-5 was fixing in the other direction, in the same commit.

Note this is **not** an argument for reverting B-6 — erasing the other hook's seen-set was a real defect.
It is that `replace` was carrying a second job (bounding the file) which the fix dropped silently. The
missing piece is a bound on `ids` (a cap, or carrying only what is still inside the window), which is a
decision, not a typo — hence P1 rather than a patch suggestion.

**Mutation, to establish the new guards are not vacuous**: `: [...newIds, ...carried];` → `: newIds;`
(sha `aa9f93fcca1232e6` → `c95b3cae8eb30d3b`, line 139 printed as mutated) reds 3 cases —
`injected-ids-marker.test.mjs` "replace writes newIds verbatim…", "does not erase another hook's ids",
`pathA-exclude-inert.test.mjs` "the writer still stringifies…". Restored to `aa9f93fcca1232e6`.
The guards are live. None of them observes the file's SIZE, which is why the regression rode in green.

## 2. P2 — 已证实 — `scrubFilePath` truncates a path at the first KV-shaped credential, destroying the basename; two different files then share one recall key

`lib/scrub-record.mjs:90-91`, `lib/file-edge-match.mjs:264`

```js
export function scrubFilePath(p) {
  return scrubSecrets(String(p ?? ''));
}
```

Eight of `SECRET_PATTERNS` use a value class that does **not** exclude `/` —
`secret-scrub.mjs:33, 74, 78, 83, 98` (`[^\s,;'"}\]]{6,}`), `:109` (`[^\s'"]{6,}`), `:259, :260`. On prose
that is correct. On a **path** it eats the separator and everything after it, including the filename.

**Reproduced** (`scratchpad/probe/collide.mjs`):

```
/repo/key-0123456789abcdef0123456789abcdef/notes.mjs
  -> /repo/***/notes.mjs          basename notes.mjs -> notes.mjs   KEPT=true
/repo/npm_AbCdEfGhIjKlMnOpQrStUvWxYz0123456789/notes.mjs
  -> /repo/***/notes.mjs          basename notes.mjs -> notes.mjs   KEPT=true
/repo/api_key=sk_live_AbCdEf0123456789AbCd/notes.mjs
  -> /repo/api_key=***            basename notes.mjs -> api_key=*** KEPT=false
/repo/token=AbCdEf0123456789/notes.mjs
  -> /repo/token=***              basename notes.mjs -> token=***   KEPT=false
```

Two consequences, both on the WRITE path this commit added (`lib/save-observation.mjs:178-181`,
`lib/activity.mjs:70`, `hook-llm.mjs:360-361`, `lib/import-jsonl.mjs:163-179`):

1. The stored value is no longer a path. `observation_files.filename`, `observations.files_modified`,
   `events.file_paths` receive `/repo/api_key=***`. The filename is destroyed at write time and cannot be
   recovered — the same irreversible-write failure `secret-scrub.mjs:43-50` records for the prose arm
   ("scrubbing runs on the WRITE path … was stored irreversibly").
2. Distinct files under such a directory collapse to ONE recall key. Same probe:

```
  stored for alpha.mjs: "/repo/api_key=***"
  stored for beta.mjs : "/repo/api_key=***"
  querying alpha.mjs returns obs ids: [1,2]
  querying an UNRELATED third file in that dir (gamma.mjs): [1,2]
```

Lessons about `alpha.mjs` are now returned for a file that was never touched, and `gamma.mjs` — which has no
observation at all — recalls both.

This also **falsifies a claim in the shipped docblock**, `lib/file-edge-match.mjs:250-252`:

```
 * unreachable through the file itself. A credential confined to a directory
 * segment is invisible to this, which is why the guard for it uses the basename
 * shape; a case built on the directory shape passes with the reader unscrubbed.
```

True for the prefix-anchored patterns (rows 1-2 above), false for the KV family (rows 3-4): a dir-segment
credential of that shape rewrites the basename too. The claim is load-bearing — it is the stated reason the
fixture uses the basename shape — and the mutation confirms the current fixture set does not distinguish
them: reverting the reader (`const filePath = scrubFilePath(rawFilePath);` → `= rawFilePath;`,
sha `1edf43f896cf6278` → `099bf15ed5af3d37`) reds exactly ONE case,
`secret-scrub-coverage.test.mjs` "recallByFile still finds a row whose stored path was scrubbed in the
BASENAME". Restored to `1edf43f896cf6278`.

The maintainer's census (0 of 2340 stored path values changed) does not bound this: the census measured the
*old* corpus, where nothing was scrubbed. It says nothing about how often a future path trips a KV pattern,
and the 3 live `events.file_paths` elements it DID find changed are not identified by pattern, so it is not
known whether they are the truncating shape.

## 3. P2 — 已证实 — the reader moved and the stored rows did not: pre-6.8.2 rows whose path scrubs are now unreachable through their own file

`lib/file-edge-match.mjs:263-269`. The commit message defers the data migration to D#49 with "Existing rows
are not rewritten here". That states the leak persists. It does not state the other half: because
`fileMatchParams` now scrubs the QUERY path, an existing raw row and a raw on-disk query no longer derive
the same key — recall that worked before this release stops working.

**Reproduced** (`scratchpad/probe/oldrows.mjs`, `:memory:` DB, real `fileMatchClause` + `fileMatchParams`):

```
basename credential   /repo/src/ghp_….mjs   OLD row reachable by a raw query: false
dir-segment (KV)      /repo/api_key=…/notes.mjs  OLD row reachable by a raw query: false
password= in a dir    /home/u/build/password=…/out.js  OLD row reachable by a raw query: false
ordinary path         /repo/lib/file-edge-match.mjs    OLD row reachable by a raw query: true
```

Population is exactly the rows the fix cares about — a row is affected iff `scrubSecrets` changes its path,
which is the definition of a leaking row. On the maintainer's corpus that is 0 junction rows and 3
`events.file_paths` elements, so the blast radius there is small; on any other install it is unmeasured. The
direction is that the fix makes the *already-leaked* rows the unreachable ones.

Same shape in the events leg: `scripts/pre-tool-recall.js:548` derives `keyPath` and `:663` builds
`fullPathNeedle` from it, so a pre-6.8.2 `events.file_paths` row with a dir-segment credential loses the
full-path arm of the match.

## 4. P3 — 已证实 — the D#N deferred leg is gated by `MAX_SESSION_INJECTIONS` and can never charge it

`scripts/user-prompt-search.js:778` gates the deterministic D#N injection on
`shouldSkipByDedup(dedupIds, injectedIdsFile, …)`, which reads the cap at
`scripts/prompt-search-utils.mjs:243`. Its write, `scripts/user-prompt-search.js:797-801`, passes
`mode:'union'` and no `bumpUpsCount`. Before B-5 that write bumped `count`, which WAS the cap, so the leg
charged the gate it read. Now the gated population is {main leg, D#N leg} and the charged population is
{main leg}.

**Reproduced** (`scratchpad/probe/cap.mjs`):

```
(a) 30 deferred-leg emissions -> count=30 upsCount=0 (cap=15)
    the 31st D#N emission is suppressed? false
```

Net direction is more injection from the D#N leg, not less, so this is not a silencing bug — it is the same
spender≠charged mismatch B-5 fixed, left in place on the sibling call site the commit does not mention. Worth
deciding explicitly (charge it, or state that this surface is deliberately uncapped) rather than leaving the
gate half-wired.

## 5. P3 — 已证实 — `count` was partitioned by writer; `ts`, which decides whether `upsCount` counts, was not

`lib/injected-ids.mjs:144-146` writes `ts: Date.now()` on every write from every caller, and
`readInjectedMarker:79` returns the zeroed `empty` (including `upsCount: 0`) once `ts` is stale. So whether
the UPS face's own budget survives a gap is decided by the OTHER hook's activity.

**Reproduced** (`scratchpad/probe/clock.mjs`) — two sessions with byte-identical UPS behaviour, 15 emissions
8 minutes apart (i.e. always beyond the 5-minute window), differing only in whether pre-tool-recall also
writes 4 minutes in:

```
pre-tool-recall active=false  upsCount= 1  16th UPS prompt suppressed=false
pre-tool-recall active=true   upsCount=15  16th UPS prompt suppressed=true
```

B-5's premise is "a budget has to be charged to the spender". The counter is now the spender's; the clock
that keeps the counter alive is still shared, so a tool-heavy session still spends the fyi face's budget —
by extending it rather than by incrementing it. Smaller than the original B-5 (15 tool-triggered writes no
longer zero the budget outright), but the same coupling.
