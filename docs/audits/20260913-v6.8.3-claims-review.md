## FALSE — ranked by how much the error misleads a future reader

### 1. The NOMEM is attributed to the wrong damage target (FALSE)

> "randomblob(32) into the leaf pages   29/30 SQLITE_CORRUPT_VTAB, 1/30 SQLITE_NOMEM"
> — commit 3da8785

The **rate** reproduces; the **attribution** does not. The mode that produced the NOMEM is the
test header's `WHERE id > 1`, which overwrites the **structure record (id=10)** as well as the
leaf page. Leaf pages alone never produced a NOMEM.

The fixture has exactly three rows — `id=1` (averages, 9 B), `id=10` (structure, 12 B),
`id=137438953473` (the single leaf page, 167 B) — so `id > 1` is *not* "the leaf pages".

`node work/claims/probe2.mjs <tree> 200`:

```
randomblob id>1  (structure+leaf)  SQLITE_CORRUPT_VTAB=195/200  SQLITE_NOMEM=5/200
randomblob id>10 (leaf only)       SQLITE_CORRUPT_VTAB=200/200
randomblob id=10 (structure only)  SQLITE_CORRUPT_VTAB=189/200  SQLITE_NOMEM=11/200
DELETE id>10                       SQLITE_CORRUPT_VTAB=200/200
```

Re-run a second time at N=200 (independent sample):

```
randomblob id>1  (structure+leaf)  SQLITE_CORRUPT_VTAB=196/200  SQLITE_NOMEM=4/200
randomblob id>10 (leaf only)       SQLITE_CORRUPT_VTAB=200/200
randomblob id=10 (structure only)  SQLITE_CORRUPT_VTAB=195/200  SQLITE_NOMEM=5/200
DELETE id>10                       SQLITE_CORRUPT_VTAB=200/200
```

The leaf-only arm is **400/400 SQLITE_CORRUPT_VTAB, zero NOMEM, across both runs**; every NOMEM
observed in 800 trials came from a mode that includes the structure record.

Correct statement: **`randomblob(32)` over the structure record — `WHERE id > 1`, which
includes id=10 — yields ~97-98% SQLITE_CORRUPT_VTAB / ~2-3% SQLITE_NOMEM (5/200 and 4/200 in
two runs). Damaging only the leaf pages (`WHERE id > 10`) yields SQLITE_CORRUPT_VTAB 400/400.**

Why it matters: the NOMEM boundary is the justification for a deliberate design decision (not
widening `isFtsCorruptionError`) and it is pinned by a test. A reader who trusts "leaf pages"
and re-measures `WHERE id > 10` gets 0/N NOMEM and concludes the boundary test is vacuous. The
decision is still right — it is the reason given for it that is wrong.

Also: the `29/30 … 1/30` split is a single 30-trial sample presented as a rate. My own first
30-trial run reproduced 29/30 + 1/30 exactly, but at N=200 the same mode reads 5/200. State the
denominator you actually want the reader to use.

Sites to fix: commit 3da8785 body only. `lib/db-unusable.mjs:89` and the test header both say
`randomblob(32)` without claiming "leaf pages", so they are not wrong — but 89 quotes the SQL
with the `WHERE` dropped. That literal statement measures 192/200 CORRUPT_VTAB, 8/200 NOMEM
(`probe3.mjs`), close enough not to mislead, but it is not the statement that was run.

### 2. "three never converge" over-counts its own table by one (FALSE)

> "Four damage shapes measured; three never converge and one destroys user content"
> — commit 6a8d34c, and `tests/claudemd-orphan-sentinel.test.mjs:17` verbatim

The table directly beneath that sentence does not say "never converges" for `end deleted` — it
says "2nd adopt DELETES user text". Measured pre-fix, `end deleted` **does** converge, at
iteration 3, to a single well-formed block — by eating the user's runbook. Only two shapes
never converge.

`node work/claims/steps.mjs work/claims/tree-prefix` (40 adopt iterations per shape):

```
end deleted          unadopt="absent" | begin=2/end=1 | converged@iter=3     | STEP ONE=0
begin deleted        unadopt="absent" | begin=1/end=2 | NEVER(40 iters)      | STEP ONE=1
```

Correct statement: **two never converge, one converges by destroying user content, one is
already fine.**

A precision note on the two NEVER rows, which strengthens rather than weakens them: the file
becomes *stable* (further adopts are no-ops) but stays malformed forever — `begin deleted`
holds a permanent extra `:end`, `version tag broken` holds the block twice. "Never converges"
means never returns to one well-formed block, which is what the 40-iteration probe shows.

### 4. The `--all` sweep survival is attributed to the wrong mechanism (FALSE)

> "(b) removeManaged must not answer 'absent' … That report is what let the orphan survive

return value for an orphan-only project, because it gates on `hasResidue` first:

`adopt-cli.mjs:412` — `if (!claudeMdHasResidue(dir, PLUGIN_SLUG)) continue;`

So the `--all` blindness was caused by `hasResidue` not counting unpaired sentinels — a
*different* repair in the same commit — not by the `'absent'` report. Mutation MUT-F (drop the
`orphanSentinelCount(blk.raw, slug) > 0 ||` clause from `hasResidue`, sha
`fa29d289…` → `0ad05b02…`, syntax ok, restored identical) over five relevant suites:

```
1 failed | 56 passed (57)

```

This is the "two necessary conditions do not make a true conjunction" shape: both repairs were
needed, but each fixes a different surface. Correct statement: **the `'absent'` report is what
silenced `unadopt`; `hasResidue`'s blindness to unpaired sentinels is what let the orphan
survive the `--all` sweep.**

### 5. "measured 1296 bytes" is a character count, not a byte count (FALSE)

> "the shipped body carries the slug twice and never as a sentinel (measured 1296 bytes, zero
> `:begin` / `:end`)" — commit 6a8d34c, `claudemd.mjs:77`, and
> `tests/claudemd-orphan-sentinel.test.mjs:28`

The rest of the claim is TRUE: the slug appears exactly twice (`## claude-mem-lite — persistent
memory` and one prose mention), never as a sentinel — so repair (a) provably cannot reject a
legitimate block.

Three copies to fix: commit body, `claudemd.mjs:77`, test header `:28`. Note
`claudemd.mjs:286`'s "~1.3 KB" is correct and, ironically, closer to the real 1304.
